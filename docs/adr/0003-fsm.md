# ADR 0003 — Finite-state machine for case status lifecycle

**Date:** 2026-06-02
**Status:** Accepted
**Deciders:** Senior Dev (ClaimMix crew)

## Context

Cases move through statuses: `procesando → listo | esperando | escalado → cerrado`.
The LLM could theoretically output any status value; we need a hard boundary that no
LLM output can violate (OWASP LLM08 — Excessive Agency).

## Decision

Implement a strict FSM in `src/server/cases/fsm.ts`:

```typescript
const VALID_TRANSITIONS: Record<CaseStatus, CaseStatus[]> = {
  procesando: ["listo", "esperando", "escalado"],
  listo:      ["cerrado", "escalado"],
  esperando:  ["procesando", "escalado", "cerrado"],
  escalado:   ["listo", "cerrado"],
  cerrado:    [], // terminal
};
```

Rules:
1. The AI worker can ONLY write `listo`, `esperando`, or `escalado` — never `cerrado`.
   `cerrado` is a human-only action via `PATCH /api/cases/:id`.
2. The FSM validates every status transition before writing to the DB. Invalid transitions
   return 409 with error code `FSM_INVALID_TRANSITION`.
3. The FSM is a pure function with 100% unit test coverage (36 test cases in `tests/unit/fsm.test.ts`).

## Consequences

**Good:**
- LLM cannot directly close a case, even if prompt-injected to attempt it (LLM08 mitigation).
- Audit log always reflects the correct status trajectory.
- Business logic is centralized in one pure function, not scattered across route handlers.

**Bad:**
- All status changes must go through the FSM — no direct DB writes in scripts/seeds
  without also updating `status` correctly. `neon/seed.sql` has no comments on this;
  the rule lives here and in `src/core/case/fsm.ts` only.

## Human edges outside the graph (September 2026)

The AI worker's own writes stay inside the graph, but not unconditionally:
`setStatus` in `src/server/confirmations/orchestrate.ts` only writes while the
case is still in a status the agent starts from (or already at the target), so
a case a person moved in the meantime is left alone instead of overwritten.

Two transitions never entered `FSM_TRANSITIONS` and are guarded in the server
instead — adding them to the graph would let any route that walks it take
them, including the AI worker (LLM08, ADR 0004):

- `REAPERTURA_POR_ABANDONO` (`cerrado → info_faltante`): a case closed for
  abandonment reopens by hand to resend the same request (P8), guarded in
  `src/server/confirmations/reenvio.ts`.
- `DEVOLUCION_AL_AGENTE` (`requiere_especialista → info_faltante`, E24): a
  person who took control with «Tomar el control» hands it back; guarded in
  `patchCase` (Pro plan, WhatsApp only, same last movement it was taken with).

Both constants live in `src/core/case/fsm.ts`, next to `FSM_TRANSITIONS`, never
inside it.

## Test coverage

Every valid transition (12) and every invalid transition (24 sampled) has a corresponding
unit test asserting pass/fail. The FSM is the highest-coverage module in the codebase.
